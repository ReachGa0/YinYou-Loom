# FPGA 工程实践与踩坑记录

> 状态：活文档，**每解决一个非平凡问题就地追加一条**
> 用途：**答辩前的复习材料**。重点不是"我们做出来了什么"，而是"我们踩了什么坑、
> 怎么定位、为什么这样解决、这件事教给我们什么关于 FPGA 的道理"。
> 阅读方式：每条都按 **现象 → 定位过程 → 根因 → 解决 → 启示** 五段写。
> 涉及数字的地方都标了证据来源（仿真输出 / 综合报告 / 实机听感），可复现。

## 案例 1 · 48 kHz 音频时钟：连续推翻两次方案

**现象**：最初打算 100.8 MHz 主频，分频出 4.608 MHz 位节拍；综合前算比例时发现数学上做不到。

**定位过程**：把 Gowin rPLL 的约束逐条套上——
`f_CLKOUT = f_CLKIN × FBDIV / IDIV`、`f_VCO = f_CLKOUT × ODIV`、`fPFD = f_CLKIN / IDIV`，
且 `FBDIV ≤ 64`、`IDIV ≤ 64`、`fPFD` 必须落在 3–500 MHz。

**根因**：

| 尝试 | 问题 |
|---|---|
| 100.8 MHz | 需要 224/15 或 448/15 的比例，**超出 FBDIV/IDIV 的 64 上限** |
| 69.12 MHz | 数学可达，但 `fPFD = 27 / 25 = 1.08 MHz`，**低于 Gowin 要求的 3 MHz 下限**，布局布线必然报错 |
| **72 MHz（最终）** | `27 × 8 / 3 = 72`，`fPFD = 9 MHz`，`VCO = 576 MHz`，全部落在合法区间 |

**解决**：72 MHz 主频 + `frac_div(8/125)` 产生平均 4.608 MHz 位节拍；I2S 每帧 48 个 BCLK
→ 长期平均采样率 **48.000 kHz 精确**。

**启示**：
1. **PLL 是"带约束的数学题"**，不是"填个想要的值"。要先算边界（FBDIV/IDIV/fPFD/VCO），再谈精度。
2. 想要非整数倍频率时，**"主频 + 分数分频"比"硬凑一个奇怪的主频"稳得多**；
3. 这类失败**必须记下来**：它证明我们理解了器件约束，而不是碰巧能跑。

## 案例 2 · PLL 参数被 IP 向导悄悄改掉

**现象**：手填的 IDIV/FBDIV 在重新生成 IP 后被改成了别的值。

**根因**：Gowin IP Wizard 偏好"简洁比值"，会归一化用户输入。

**解决**：不再用向导重新生成；以 `fpga/loom/src/gowin_rpll/gowin_rpll.v` 里的 `defparam` 为唯一事实来源，
并在 `README` 里明确写"勿再打开向导重新生成"。

**启示**：**生成式工具的产物要当成"外部输入"来校验**。工具帮你"优化"过一次，你的设计文档就与代码脱钩了。

## 案例 3 · 波表没被推断成 BSRAM

**现象**：预期波表占用块存储，实际综合报告显示落在 LUT 里（P2 遗留项，移到 P3 才验证）。

**根因**：存储推断（inference）对代码风格敏感——读地址是否同步、是否有复位、复位值是否可映射等。

**解决**：按同步读 + 无复位数据路径的写法组织 `wavetable_rom.v`，并用综合报告确认 BSRAM 块数。

**启示**：**"存大数组"不等于"用块存储"**。唯一可信的判据是综合报告里的 BSRAM/DSP 计数。

## 案例 4 · 四声部齐按削顶（归一化必须在饱和之前）

**现象**：四键同时按下时破音。

**根因**：每个声部按单音满幅设计，四路相加超出 16 位范围；限幅器（saturate）把波形削成方波 → 严重的谐波失真。

**解决**：在 mixer 里**先按同时发声数缩放、再做饱和限幅**（1/1、1/2、21/64≈1/3、1/4），
用移位 + 加减实现，不引入除法器。

**启示**：
1. 多声部系统的"总能量预算"要在架构层解决，**不能指望限幅器兜底**；
2. 归一化放在饱和**之前**，限幅器就只在异常情况下起作用；
3. 21/64 与 1/3 相差约 0.045 dB——**用近似换硬件代价**是这类工程的常规取舍。

## 案例 5 · 按第二个键时一声"咔"（增益跳变）

**现象**：按住 A 正常；再按 B 出现一声"咔"，松开 B 又一声。清声（dry）更响却完全干净。

**定位过程**：
1. 先怀疑电平过大 → 用"Lo/Hi 电平开关"对比，**Lo 也破** → 排除模拟端过载；
2. 再查混合级：归一化系数是**按同时发声数**查表得到的，而计数一变化系数就**瞬间跳变** → 正在响的音幅度被瞬间砍半 → 一阶不连续 = 一次"咔"。

**根因**：增益是"阶跃"而不是"连续变化"。

**解决（两处）**：
1. 计数口径改为"**仍在发声**的声部数"（`gate | ADSR busy`）——否则最后一个音松开时计数立刻掉到 0，还在响的释放尾音会被放大 4 倍；
2. 增益改成**每样本限幅步进的斜坡**（Q15、每样本最多变 128，约 2.7 ms 走完 1/1→1/2）。

**启示**：
1. **任何"按条件切换的增益"都要考虑它切换时对已有信号做了什么**；
2. 排查音频问题要**先做对照实验**（Lo/Hi、冻结 LFO），再改代码——对照实验比猜快得多；
3. 斜坡的代价是"变化变慢"，在演奏类系统里这通常是可以接受的。

## 案例 6 · 松开最后一个音，尾音突然变大

**现象**：多声部归一化做好之后，最后一个音松开的瞬间尾音音量跳一下。

**根因**：归一化统计的是 `gate`（按键状态），而 note_off 之后 gate 立刻变 0 → 计数 4→0 → 系数从 1/4 跳回 1/1，
**但此时三个声部的 ADSR 释放还没结束**，还在发声 → 尾音被瞬间放大。

**解决**：统计口径改为 `gate | busy`（busy 来自 ADSR 的"仍在发声"标志），尾音收完计数才归零。

**启示**：**"信号存在"和"信号有声"是两件事**。做动态资源统计时，要选与"听觉上还在发声"一致的那个口径。

## 案例 7 · 叠置和弦丢音，且看起来"随机"

**现象**：按住 A 的和弦再按 B 的和弦，松开 B 后 A 的和弦只剩一个音，而且**每次剩下的音不一样**，偶尔完全不响。

**定位过程**：把声部分配器的行为逐拍推演出来——

| 事件 | 4 个声部的占用 |
|---|---|
| 按 A | v0=60, v1=64, v2=67 |
| 按 B 第 1 音 64 | v3=64 |
| 按 B 第 2 音 68 | 无空闲 → **抢占 v0**（A 的根音被顶掉） |
| 按 B 第 3 音 71 | 无空闲 → **抢占 v1**（A 的三度被顶掉） |
| 松 B → 发 64/68/71 的 note_off | v3/v0/v1 被释放 |
| 结果 | 只剩 v2=67（A 的五度） |

**第二个隐藏问题**：释放是按 `note_id` 匹配的，而 A 的 E4 与 B 的根音都是 64 → 松开 B 会**误杀 A 的 E4**。

**根因**：4 个声部放不下两个三音和弦（6 音）；"叠加和弦"这个交互语义本身就超出了当前的声部预算。

**解决**：**改交互语义**——同一时刻只允许一个和弦在响，采用"**最近按下优先**"（last-note priority）：
按住 A 再按 B 响 B；松开 B 回到 A；换和弦时先释放旧和弦、等 ADSR 释放结束（约 34 ms）再起新和弦。

**启示**：
1. **资源不足时，"改需求"往往比"堆资源"更好**：不扩声部、不动共享模块，问题从根上消失；
2. 多声部系统里 **note_id 是"释放匹配键"**，不同来源共用同一 id 会互相误杀——这是设计接口时就要想清楚的事；
3. 行为要可预期：**随机丢音是最糟的体验**，宁可限制功能也要确定。

## 案例 8 · 合唱持续破音（本工程最有价值的一次排查）

**现象**：开启合唱后，正弦**单音**也持续破音；清声（dry）比合唱更响却完全干净。

**定位过程（教科书式的三步）**：
1. **排除电平**：dry 更响不破 → 不是过载、不是"相加忘了除 2"（源码里本来就是 `(dry + wet) >> 1`）；
2. **确认是合唱支路**：单音也破、和弦也破、dry 不破 → 问题 100% 在 `chorus.v` 内部；
3. **对照实验**：把 LFO 步长设为 0（延迟冻结不动）→ **破音消失** → 锁定"读指针在动"这件事。

**根因**：延迟读指针是**整数样本步进**——LFO 每 256 个样本让延迟量跳 1 个样本（≈ 5.3 ms 一次），
等于在波形上周期性插入一阶不连续点，重复频率约 **187 次/秒** → 听感就是持续的粗糙/破音。

**解决**：改成**分数延迟 + 线性插值**——LFO 拆成 8 位整数部分 + 8 位小数（Q8），
每样本取相邻两个抽头 `a`、`b`，输出 `a + (b − a) × frac`；两个抽头用同一存储端口分时读。
代价：+1 个乘法器（DSP 3→3.5 块）、BSRAM 7→9 块、Logic +110。

**启示**：
1. **可听现象必须转成可测量的量**（"每 5.3 ms 跳一次"就是可测的）；
2. **对照实验是最快的定位手段**（冻结 LFO 一下就把范围从"整个音频链路"缩到"读地址"）；
3. **标准解往往就是"别人为什么那样做"**：专业合唱都做分数延迟插值，不是炫技，是因为整数步进必然产生这种失真；
4. 改造过程中我自己一度改出**丢掉 dry/wet 混合**的错误（输出变成 100% 湿声），是测试台抓出来的 → **改造要有测试兜底**。

## 案例 9 · 综合器把顶层选错，P&R 报"所有端口都找不到"

**现象**：布局布线阶段报 `Can't find object named 'clk' / 'key_n[0]' …`——**每一个**端口都找不到。

**定位过程**：报错信息指向"约束"，但真正的问题在综合：日志末尾写着
`NOTE (EX0101) : Current top module is "input_map"` ——综合器把一个**已不再使用、但还留在工程文件清单里**的模块当成了顶层。

**解决**：① 把不再使用的源文件移出工程清单；② 在工程配置里**显式指定** `TopModule`。

**启示**：
1. **报错的位置 ≠ 原因的位置**。P&R 报的是"结果"，要回到综合日志找"起点"；
2. 工程越大越要**显式声明顶层**，不要依赖工具自动识别；
3. 清理"不再使用的源文件"是工程卫生，不是小事。

## 案例 10 · 一个被误判的警告：`is swept in optimizing`

**现象**：综合警告说某个实例被"优化掉"，我们担心功能被删。查了层次报告、网表、引脚表都判不出来。

**解决**：**用一块位流上板验证**——按键功能正常，说明逻辑只是被**内联进父模块**，警告无害。

**启示**：
1. 警告分两类："逻辑被真的删掉"和"层次被展平"；**资源计数（BSRAM/FF）能区分**（真的删掉会掉资源）；
2. 判不出来时，**用最小的实机验证一次性定性**，比继续猜更省时间；
3. 记录这类"虚警"能避免下次重复调查。

## 案例 11 · 专用引脚（SSPI）不能随便用

**现象**：同一个引脚在其他工程能用，新建工程却报
`ERROR (PR2017): 'i2s_din' cannot be placed according to constraint, for the location is a dedicated pin (SSPI)`。

**根因**：PIN54–56 属于外部配置 Flash 的 SSPI 专用引脚；旧工程在 GUI 里勾选过"放开 SSPI"，而新工程是默认配置。

**解决**：把旧工程的 `impl/<project>_process_config.json` 复制到新工程并把 `"SSPI"` 设为 `true`。

**启示**：
1. **引脚能不能用，常由"工程配置"决定，而不是代码**；
2. 新建工程时要**对照一个已验证工程**核对配置项，别从零开始。

## 案例 13 · 测试台"全绿"却抓不到错（空跑）

**现象（三种）**：
1. 长回波用例用"采样 `valid` 电平"判断——而下一轮 TRIG 已经把它清掉了，**检查被绕过**；
2. 测试台数组按 3 个脉冲分配，后面越界读到 `x`，报出一堆假 FAIL；
3. 改了 DUT 的流水深度（3 拍 → 4 拍），测试台还在按旧拍数等 → 全部读到 0。

**解决**：① 用"**上升沿计数**"等随时间稳定的判据，不用瞬时电平；② 数组按最大脉冲数分配；
③ 测试台改成**等有效脉冲**而不是数固定周期。

**启示**：
1. "测试通过"本身也需要被验证——**变异测试**（故意把 DUT 改坏，确认测试台会红）是有效手段：
   本工程对超声波（改错距离常数）与测试模式（改错频率表）各做过一次，都成功抓到；
2. 测试台的判据要选**不会被时间边界影响**的量；
3. **改动 DUT 的时序结构必须同步测试台**，否则测的是过期期望。

## 案例 14 · 异步输入的亚稳态与"两级同步"为什么够

**现象**：超声波 ECHO 是外部异步信号，边沿可能正好落在时钟沿附近。

**解决**：两级同步器（`echo_s0 → echo_s1 → echo_s1d`），状态机**只使用同步后的值**和由它派生的边沿脉冲。

**为什么够**：亚稳态概率随同步级数指数下降；**这个概率仿真证明不了**，只能靠结构与时序约束保证。
另外：上升/下降沿经过**同一组同步器**，延迟相互抵消 → `t_fall − t_rise` 只留 ±1 µs 量化误差。

**启示**：
1. 跨时钟域/异步输入的处理是**结构问题**，不是"多仿真几次"能解决的；
2. 设计时要主动利用"共模抵消"这类性质（同路径延迟在差值里消掉）。

## 案例 15 · 要不要用 MCU 分担显示？（合规判断的方法论）

**问题**：OLED 刷新与波形动画会不会拖垮 FPGA？能不能外挂 STM 分担？

**定位过程**：**先查官方原文，再谈技术**。用 pypdf 提取《选题指南》文本后按行核对：
——"不使用 MCU"出现在**选题四（开放型题目）**；选题二（我们的选题）的红线全部围绕
**音频生成通路**（HDL 逐样本、≤10 ms、杜绝软件串行运算、严禁预录/推流/整段触发）。

**结论**：① 官方未禁止固定功能专用芯片（DAC、显示驱动、ADC、触摸控制器都是外围器件）；
② 我们自己的 `AGENTS.md` 定了更严的规矩（最终作品不含任何可编程器件参与功能），因此**保持纯 FPGA**；
③ 调试阶段允许临时用其他 MCU 做采集/信号发生，但不得进入位流、PCB、BOM 与报告。

**启示**：
1. **合规问题先查原文，不凭印象**；引用要能定位到行；
2. 自定约束可以比官方更严，但要写清边界（"固定功能器件" vs "可编程器件"）；
3. 答辩口径要提前写好：*"本作品唯一的可编程器件是 FPGA，音频链路的每一级都是 HDL 硬件逻辑；板上其他芯片都是固定功能专用器件。"*

## 案例 16 · DC 悬空导致"白屏"，并顺手废掉三档速度实验

**现象**：2.4 寸 ST7789（SPI）TFT 第一次上板，屏幕**均匀纯白**——背光亮，但没有任何图案、也没有花屏或噪点。
把 SCLK 从 12 MHz 降到 2.25 MHz、再降到 1 MHz（还加了周期性整屏重画），**三次都是同样的纯白**。

**定位过程**：

1. 先查模块前级。原理图上 5 根信号线（SCL/SDA/CS/DC/RES）各串一颗 1N5819 肖特基，配 4.7k 上拉到板上 LDO 输出的
   V3.3。按图推：我们的**低电平**靠二极管正向导通传进去（面板侧被拉到 ~0.3V），**高电平**则只能靠 4.7k 上拉"喂"上来
   —— 于是推断"上升沿太慢、速度受限"，做了 12 MHz → 2.25 MHz → 1 MHz 的降速实验。
2. 做"探针位流"（5 根线各输出一个节奏不同的超慢方波，并在板载 LED 上镜像），把**"线通不通"**和**"参数对不对"**
   这两件事分开——否则两者症状都是白屏，无法区分。
3. 对照项目自己的 `docs/10_硬件引脚与资源.md` 发现：**这 6 个脚不在同一排排针上**（73/74/75 在 `J_CORE_A`，
   71/72/76 在 `J_CORE_B`）。这给了"插错孔"一个结构性诱因，也解释了为什么只写 FPGA 引脚号的接线表不够用。
4. 用户逐根核对接线时发现：**DC（数据/命令选择）悬空**，没有插到排针第 6 脚。

**根因**：DC 悬空时，模块侧那颗 4.7k 上拉把 DC 顶成**高电平**，而 DC 高 = "后面跟的是数据"。
于是我们发的每一条命令（`0x11` 睡眠退出、`0x3A` 像素格式、`0x36` 扫描方向、`0x21` 反显、`0x29` 开显示……）
都被面板当成**像素数据**吃掉 —— 初始化序列一条都没生效，面板永远停在未配置状态，只有背光在亮，看起来就是"均匀纯白"。

关键点：**这个故障与 SCLK 速度完全无关**，所以三次降速实验全部无效——三次实验都被同一个恒定故障挡在外面，作废。

**解决**：把 DC 接回排针第 6 脚，显示立即恢复；再校准两项屏参（`MADCTL=0xA0` 修正 180° 翻转、关掉反显），
色条、红边框、四角方向标记全部正确。

**启示**：

1. **"换参数没用"通常不是参数的问题，而是有一个恒定故障在挡路。** 接线没被验证之前，所有参数实验都是白做——
   这次白跑了三档速度、烧了三个位流。**先把"通路"证明一遍，再调参数。**
2. **纯白 ≠ 花屏**，两者的排查方向完全不同：花屏说明数据能到、内容错（查位序/格式/速度）；纯白说明**命令根本没被接受**，
   要把注意力放在 CS / DC / RES 这类"资格线"上，而不是数据线。
3. **接线表必须写到"哪个排针的第几个孔"**，只写 FPGA 引脚号是不够的——同一组功能脚可能分散在两排排针上
   （本板 73/74/75 与 71/72/76 就分属 `J_CORE_A` / `J_CORE_B`）。
4. **"悬空"不等于"无所谓"。** 这类控制脚悬空时的电平由**模块侧上拉**决定，等价于把面板钉死在某一个模式上；
   本次就是被钉死在"数据模式"。

**证据**：用户实测（DC 接回后立即出图）；校准后四角方向标记颜色与设计一致。

## 案例 17 · "仿真过 ≠ 可综合"再添两例：$readmemh 路径基准、括号表达式位选

**现象（两个独立问题，同一次综合里一起暴露）**：

1. 新写的 8×16 字库 ROM（`$readmemh` 载入 `data/fonts/font8x16.hex`）在 Icarus 仿真里一切正常，
   但 Gowin 综合报 `WARN (EX3988): Cannot open file 'data\fonts\font8x16.hex'`，紧接着
   `WARN (NL0002): The module "font8x16_rom" ... is swept in optimizing` —— **整个 ROM 被当成全 0 常量优化掉了**
   （若直接上板，屏上一个字都不会有）。
2. `wire [3:0] x = cond ? (px_y - 8'd130)[3:0] : ...;` 这种"对括号表达式取位选"的写法，
   Icarus 编译通过，Gowin **直接报错** `ERROR (EX3863): Syntax error near '['`。

**定位过程**：

1. 第一条的关键是**相对路径的基准不是"调用 gw_sh 的目录"**：本项目用 CLI（从仓库根调用 `gw_sh tmp/build_*.tcl`）构建时，
   Gowin 按**工程目录**（`fpga/<工程>/`）解析相对路径；而 GUI 流程下音频工程的 `data/wavetables/...`
   一直是能加载的 —— 说明**两条流程的基准不同**。`loom_top.v` 里早就写着
   "$readmemh 找不到文件只会警告、ROM 会静默变全 0"，这次被真实触发了一次。
2. 第二条读报错原文即可确认：Verilog-2001 的位选只能作用于**命名线网/信号**，
   对括号表达式取位是 SystemVerilog 放宽的用法。

**解决**：

1. 把字库路径做成**参数** `FONT_INIT`：综合默认 `../../data/fonts/font8x16.hex`
   （所有 `fpga/<工程>/` 都在同一深度，所以这条相对路径通用），仿真时由测试台覆盖成
   `data/fonts/font8x16.hex`（Icarus 以仓库根为基准）—— 两条流程各自自洽。
   同时把"综合后必须确认日志里没有 readmemh 告警"写进每次构建的检查项。
2. 先把差值命名成线网再取位：`wire [7:0] d = px_y - 8'd130; ... d[3:0]`。

**启示**：

1. **"仿真通过 ≠ 可综合"在本项目已经是第三次**（前两次：同一寄存器被两个 always 块驱动；
   本次两条）。固定动作应该是：**仿真过了立刻跑一次综合，并且逐条读综合告警**。
2. **`readmemh` 这类"只警告、静默降级"的告警比报错更危险**：报错会停下来，警告会让位流"看起来很成功"地烧进去，
   然后在实机上表现为"屏是亮的但什么都没有"。凡是 ROM/表数据，构建后都要确认它真的被加载了
   （本项目的判据：综合报告里 BSRAM 计数不为 0，且没有 readmemh 告警）。
3. **同一仓库在不同入口下，相对路径的基准可能不同**。所有"文件路径"都要在两条流程里各测一次，
   或者做成参数分别给值。
4. 不要用仿真器的宽容度当语法标准：**工具越严格越好**，Gowin 拦下的这两处，Icarus 都放过了。

**证据**：Gowin V1.9.11.03 综合日志（`WARN EX3988` / `WARN NL0002` / `ERROR EX3863`）；
修完后重新构建，readmemh 告警消失、综合报告显示 `BSRAM 1/46`（字库确实进了块存储）。

## 案例 19 · "排母中心放这里会超出来"：坐标语义 + 画布 y 轴方向

**现象**：照交接文档给的摆件表，在嘉立创EDA专业版里摆 1x20 母座，填 (20, 25) 之后**器件左端伸到板框外**；

1. 先查封装原点：用 pcbnew 读回 KiCad 那份板子，`PinSocket_1x20` 放在 (20, 25) 时，
   1 脚焊盘坐标**就是** (20, 25) —— 说明那批数字是**"1 脚"的坐标，不是器件中心**。
2. 再核尺寸：1x20 母座长 20 × 2.54 = **48.26mm**。中心放在 x=20 → 左端 = 20 − 24.13 = **−4.13mm**，
   正好在板框外面 —— 与用户看到的现象吻合。
3. 最后用一个数据点定画布方向：用户把原点设成板框左上角后，板内光标 y 读数是**负值**，

② 两套工具的 **y 轴方向相反**。任一条没对齐，摆出来的位置都会错。

**解决**：

1. 交接文档里的坐标统一改成**器件中心**，并按嘉立创画布约定给**负 y**（`docs/23` §8.2）；
2. 加一条 30 秒自检：摆完 U1 后把鼠标停在它的 **1 脚焊盘**上，应显示约 `(20, −25)`；
   对不上就是"原点在 1 脚"，把中心 x 加/减半个长度即可（长条器件：1x20 差 24.13mm、1x8 差 8.89mm、
   2x10 差 11.43mm）。

**启示**：

1. **"坐标"这个词必须带三个限定**：原点在哪、是**器件中心**还是**1 脚**、y 轴朝哪。
   少一个就会出上面这种事，而且往往要到"摆上去才发现超框"才暴露。
2. **跨工具搬坐标前，先挑一个已知锚点验证**（这里是 U1 的 1 脚），再批量搬剩下的 ——
   比逐个核对 28 个器件快得多。
3. 长条器件最能暴露这类错误：短器件只偏 1.27mm，1x20 母座能偏 24mm。

**证据**：`PCB/carrier_v0/Loom_Carrier_V0.kicad_pcb` 中 `J_CORE_A` 的 pad1/pad20 = (20, 25)/(68.26, 25)；
嘉立创界面悬停 1 脚的读数 `(20, −25)`；修正后 U11 右端不再超框。

## 案例 20 · 摆件撞车：安装孔净空，以及一条被我算错的"扇出带"

**现象**：摆件阶段连出三处问题：① U12（5V 螺钉端子）本体**盖住了左上角安装孔**；② C7 与 U13 外框只差
1.25mm；③ 更隐蔽的一处 —— 我一度提议的"把 U11 信号排翻到朝上"方案，会让 U11 与核心板 B 排之间只剩
**约 1.2mm** 净空，7 根 `SPARE` 在物理上根本扇不出来。

**定位过程**：

1. 前两处由用户目视发现，用坐标一算即确认（U12 本体 x 从 4 起，安装孔在 x=5）。
2. 第三处是**重新按净空公式逐对算**时才发现：

   - 初版：U11 信号排 −40.54、B 排焊盘 −45.32 → 净空 = 45.32 − 40.54 − 0.85 × 2 = **3.08mm**

   - 最终方案：U11 整体上移到 −36.00 → 信号排 −37.27 → 净空 = **6.35mm**（7 根一层就能扇出来）。
3. 我先前把这处说成"2.5mm/6mm"，是因为把 U11 的**电源排**当成了边界，算宽了一倍 —— 属于典型的
   "凭印象算净空"。

**根因**：① 布局时只考虑"功能就近"，没按"焊盘半径 + 线宽 + 间隙"逐对算物理净空；
② 大件（螺钉端子、Ø8 电解）和机械件（安装孔）没有单独列成约束条件。

**解决**：

1. U12 右移到 (13.5, −7)、U13 下移到 (13.5, −14.5)；C8/C7/H2 挪到右上（它们只挂在 `5V_SEL` 上，
   位置不影响电路）；
2. U11 上移 3.27mm，专门给 `SPARE` 留出 **6mm 高的扇出带**；
3. 把三条硬约束写进 `docs/23` §8.6：**安装孔 4mm 净空**、**U2↔U11 扇出带 ≥6mm**、**左右竖条留空**。

**启示**：

1. **"能不能走通"必须按净空算，不能凭感觉**。2.54mm 间距的焊盘之间只有 0.84mm，
   0.4mm 的线加两侧间隙正好卡死 —— 这种地方**不要试图穿线**，从排母端部绕。
2. 布局的判据不是好看，而是"**每个连接器放在它的信号源那一侧的对面**"：
   核心板 A 排朝上、B 排朝下，A 排的信号器件就放上面、B 排的放下面，需要"跨侧"的线越少越省事。
3. **大件和机械件要单独过一遍净空**（端子、电解、安装孔），它们最容易吃掉走线通道。
4. 这一轮里"我提的方案更差、被数据推翻"这件事同样要记：**先算净空再谈方案**，
   否则改一圈还不如不改。

**证据**：`docs/23` §8.2 / §8.6；前后坐标对照（U11 −39.27 → −36.00；U12 (9, −6) → (13.5, −7)；
C7 (20.5, −11) → (76, −14)；H2 (28.5, −3.5) → (76, −6)）。

## 案例 21 · Verilog 乘法结果宽度：`wire [33:0]` 也救不了直接写 `a*b`

**现象**：摇杆弯音映射里 `1755 × 572` 应该得到约 100 万，实际只算出 21 万；换到 32 位相位增量乘 Q15 系数时同样数值异常。

**定位过程**：

1. 打印 `K_R=572`、`eff=1755`、`delta=849`，三个数单独看都对；
2. `849 × 256 ≈ 217,344 ≈ 1,003,860 mod 2^18` —— 说明乘法被截成了 18 位；
3. 检查表达式：`(eff * K_R) >> 8` 里两个操作数分别是 18 位和 16 位，Verilog 的乘法结果宽度取**较大者**（18 位），不是两者相加。

**根因**：乘法表达式的宽度由操作数决定；直接赋值给宽 wire 时，中间乘积仍可能先按窄宽度计算。

**解决**：显式声明足够宽的中间量：

```verilog
wire [33:0] prod = eff * k_sel;      // 18 + 16
wire [47:0] bend_prod = inc * bend_q15;  // 32 + 16
```

**启示**：凡是乘法，先写 `wire [A_W+B_W-1:0] prod = a * b;`，再做移位/截断。这个坑在三个模块里各踩了一次。

## 案例 22 · 单周期 `valid` 把弯音值"每毫秒打回中位"

**现象**：摇杆读数条会动，屏幕上的 `B`（`bend_q15`）却一直是 `8000`，音高完全不弯。

**启示**：**脉冲信号要么锁存、要么边沿检测**，不要拿它当使能电平一直用。

## 案例 26 · 拨弦“响完了但声部一直占着”：`busy` 语义错位

**现象**：把拨弦实现成 `sustain=0` 后，音确实衰减到 0 了，但按住键不放时 `voice_busy` 一直是 1：混音归一化把静音声部算进去，切 MODE 也被卡住，新音还会被抢占。

**定位过程**：`voice_adsr` 的 `S_SUSTAIN` 分支无条件 `busy <= 1'b1`。`busy` 表示“状态机没回 IDLE”，不是“还有声音”。sustain=0 时 level 已为 0，但状态永远停在 SUSTAIN。

**根因**：`busy` 的语义与其消费者（`voice_alloc` 的声部复用、`mixer` 的归一化、`chord_map` 的换和弦等待）不一致。

**解决**：

1. `voice_adsr` 增加 `one_shot`；拨弦在 `S_SUSTAIN` 直接回到 `S_IDLE` 并拉低 `busy`；
2. 增加 `gate_consumed`：拨弦结束后按键仍按着也不重触发，松手后清零；
3. 拨弦参数 `sustain=0、D/R step=4`（约 340ms 衰减）；
4. 仿真验证：gate 一直为 1，约 13 万拍后 `voice_busy=0`、`mix=0`。

**启示**：**`busy` 是给“谁”用的，就要按那个消费者的语义定义**；一个标志同时服务分配/混音/状态机时，语义必须写清楚。

## 案例 27 · “功能对、仿真过”仍会把 72 MHz 时序压垮

**现象**：把 Y 轴真正接入 note-on 力度后，功能和单元仿真都正确，但 Gowin 首次
综合出现 157 个 setup 违例端点，最差 slack 达到 `-16.341 ns`。加入中值滤波和
寄存器后仍有 16 个端点违例，其中最差 `-0.139 ns`。

**定位过程**：

1. 读取 `p6_test_demo.timing_paths`，最差路径从 `joy_filter/filtered_out`
   穿过 `expression_map` 的减法、死区、乘法，再进入声部分配；
2. 将中值、低通和力度/expression 映射拆成多级流水后，违例降到 16 个；
3. 下一版最差路径变成 `press_pulse → input_map → engine_note_inc`；
4. 在演奏事件送入 synth_engine 前增加一拍事件寄存，最终 setup/hold 均为 0。

**根因**：几个单独看都不复杂的组合逻辑被串成了同一条长路径。仿真只检查功能，
不会替设计者检查 72 MHz 下这些组合级能否在一个周期内稳定。

**解决**：

- `joy_filter`：原始样本、3 点中值、低通分别设流水级；
- `expression_map`：减法、绝对值/死区、乘法、力度、expression 分级；
- `pitch_bend_map`：弯音减法、幅值、乘法和限幅分级；
- 演奏事件在进入合成引擎前寄存一拍；
- 每次改 RTL 后都重跑综合并读取 setup/hold，而不是只看仿真 PASS。

**启示**：**“仿真通过”只证明功能成立，“综合通过”也不等于时序成立。**
实时输入一旦接入音频链路，必须同时检查资源与时序；寄存器不是性能装饰，
而是把长组合路径切成可收敛的流水级。

## 案例 28 · 32 声部不是把 `4` 改成 `32`：先过资源上限，再过时序

**现象**：把 `VOICES` 从 4 改为 32 后，首次综合估算需要约 26879 个 LUT，
超过 Tang Nano 20K 的 20736；把逐音增益乘法移入 mixer 后，逻辑仍约
39835（20299 LUT + 19536 ALU），依然放不下。

**定位过程**：

1. 原架构每个声部都有“波形×包络”“包络×力度”“频率×弯音”三条乘法链；
2. 4 声部可以接受，32 份复制后 DSP 和 LUT 同时膨胀；
3. 把逐音力度乘法移到 mixer 的逐声部累加阶段，只为当前有效声部计算一次；
4. 把弯音乘法移到 `bend_scan.v`，每采样周期顺序扫描 32 个声部；
5. 弯音扫描又出现 32:1 选择直接接乘法的长路径，因此把选择和乘法拆成两级。

**结果**：

- Logic 10938/20736（53%）；
- DSP 22/24（92%）；
- BSRAM 20/46；
- setup/hold 均为 0 违例，最差 setup slack `+0.391 ns`；
- 32 路 4096 点仿真频谱可识别全部 32 个目标峰。

**启示**：高复音设计首先是**架构问题**，不是参数问题。FPGA 有足够时钟余量时，
“按声部顺序共享一个乘法器”通常比复制 32 份并行乘法更适合低资源器件；
但“顺序累加”仍要加流水，否则 32:1 选择会变成长组合路径。

## 案例 29 · 为了压时序寄存像素，却把字模寄存到了“上一拍”

**现象**：32 声部位流音频正常，但 TFT 上部分文字出现缺笔或错位。

**定位过程**：

1. `ui_render` 的字库 ROM 是同步读，地址变化后要下一拍才输出字模；
2. 为降低 `ph_acc → 像素` 的组合路径，曾给 `px_data` 再加一级寄存器；
3. 该寄存器与字库 ROM 的更新发生在同一拍，因此捕获到的是上一拍字模；
4. 原测试台只统计文字区亮点数量，没有逐字符比对，所以仍显示 PASS；
5. 删除合成占位波形后，UI 长路径已经消失，可以直接恢复 `px_data` 组合输出；
6. 测试台增加 `check_glyph`，逐像素核对 TONE / SINE / MODE / TEST 等字模。

**结果**：文字时序恢复正确，`tb_ui_render` 46 项检查通过；重新综合后
setup/hold 仍为 0，最差 setup slack `+0.391 ns`。

**启示**：测试如果只检查“有没有字”，无法发现“字错了一拍”。对于有同步读 ROM
的像素接口，必须同时验证时序契约和具体字模内容。

## 案例 30 · 四路混响不能强行塞进一个 RAM：要按端口结构拆分

**现象**：新增 250 ms 延迟和四路混响后，仿真全部通过，但 Gowin 首次综合
报告约 9.7 万 DFF，远超 15750。仅看 `$readmemh`/数组写法，很容易误以为
“已经推断成 RAM”。

**定位过程**：

1. 查看 SUG949，Gowin 要求 RAM 使用明确的同步读写模板，也可用
   `syn_ramstyle="block_ram"` 强制；
2. 最初把四条混响线放在一个 `line_mem` 中，用四个不同写地址复用同一块存储，
   综合器警告该 block-RAM 属性不适用，数组回落到寄存器；
3. 把混响改成四个独立小数组 `line0..line3`，每个只保留一个读口和一个写口；
4. 250 ms 延迟使用单独的大数组，不再和混响共享地址空间；
5. 保持所有 RAM 读写都在状态机中分时发生。

**结果**：

- 延迟和四路混响都成功推断为 BSRAM；
- BSRAM 使用量 43/46，DSP 21/24；
- 全量回归 44/44；
- setup/hold 0/0，最差 setup slack `+0.044 ns`。

**启示**：数组“看起来像 RAM”不等于综合器能映射。多路不同写地址的伪 RAM
结构应拆成多个单读写口存储；同时要用 Gowin 的资源报告确认推断结果，不能只看
Verilog 仿真 PASS。

## 案例 31 · 单块 RAM 复用三档 FX：既要固定端口，也要尊重同步读延迟

**现象**：把 CHORUS、DELAY、REVERB 改为共用一块 16384×16 数组后，
Gowin 能打印 `Extracting RAM for identifier 'fx_mem'`，却没有真正映射成
BSRAM，而是回退成约 16K 个寄存器，综合报 228774 个 DFF。只加
`syn_ramstyle="block_ram"` 仍无法解决。

**定位过程**：

1. 共享数组同时包含清零写口和三种效果的多个读、写地址，端口结构不够固定；
2. 先抽出 `fx_shared_ram`，只保留一个同步读口、一个同步写口和固定读延迟；
3. 综合成功，BSRAM 从 43/46 降到 32/46，说明存储复用本身可行；
4. 首次布局布线在合唱路径出现 18 个 setup 违例，最差 `-1.037 ns`；
5. 把“乘法 → 插值 → 混合 → 渐变”拆成流水寄存器后，0/0 违例；
6. 原 `tb_fx_engine` 只判断输出非零，没有发现同步 BSRAM 比直接数组晚一拍；
   测试改为切模后先清空共享区，再输入脉冲，并按 4 个样本后的延迟抽头精确检查；
7. 在每次读地址后补等待状态，使状态机在 `rdata` 已寄存后才取样。

**结果**：

- 全量回归 44/44；
- Logic 12379/20736、Register 6954/15750；
- BSRAM 32/46（相对独立 FX 的 43/46 节省 11 块）；
- DSP 仍为 21/24；
- setup/hold 0/0，最差 setup slack `+0.252 ns`；
- 最终位流已烧录，读回 User Code `0x0000413C`。

**启示**：推断出 RAM 和“读回正确的数据”是两件事。直接数组读在仿真里可能像
组合逻辑，但真正映射成 BSRAM 后是同步读；状态机必须给读延迟留一拍。测试也不能
只检查“有声音”，要用已知脉冲和已知延迟确认数据路径没有错位。

## 案例 32 · 混响“电流声”来自反馈增益写错，不是 BSRAM 本身

**现象**：FX 共享存储版烧录后，DRY、CHORUS、DELAY 正常，进入 REVERB 后
出现持续电流声或破音；普通演奏 32 声部没有异常。

**定位过程**：

1. 只有 REVERB 异常，排除共享 RAM 地址和数据通路整体失效；
2. 检查四路反馈公式发现，注释写“反馈约 0.625”，实际代码为
   `tap - (tap >>> 3)`，即 **0.875**；
3. 0.875 反馈让短延迟线稳态增益达 8 倍，满幅音频在写入 16 位缓冲前持续削波；
   削波产生的高次谐波又进入反馈环，形成持续破音；
4. 原测试只输入单个脉冲并检查尾音非零，没有覆盖满幅持续输入和共振稳态，
   因而没有在仿真阶段暴露问题；
5. 先把反馈修正为 `(tap >>> 1) + (tap >>> 3)`，约 0.625；持续强信号测试仍
   记录到 13209 次内部饱和；
6. 将每路线路输入降为干声的 1/4，输出改为半干声加半湿声；
   理论内部稳态峰值低于满幅，输出叠加也保持在 16 位范围内；
7. 新增满幅共振脉冲、持续强方波和精确首轮回声检查；
8. 增益修正使混音器原有临界路径出现 `-0.184 ns` setup 违例，因此给
   `total × gain` 乘积增加一级流水，重新收敛。

**结果**：

- 混响内部削波计数为 0；
- 全量回归 44/44；
- Logic 12436/20736、Register 6977/15750；
- BSRAM 32/46、DSP 21/24 保持不变；
- setup/hold 0/0，最差 setup slack `+0.365 ns`；
- 最终位流已烧录，读回 User Code `0x000000D7`。

**启示**：音频算法不能只检查“有输出”，必须检查增益边界、稳态和最坏输入。
反馈系数、输入注入和干湿混合要作为一组增益预算设计；一个系数的注释与实现
不一致，就可能把稳定算法变成持续削波器。
