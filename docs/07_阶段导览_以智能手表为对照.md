# 以智能手表为对照：吟游 Loom 会走过哪些阶段

> 写给有 STM32 智能手表项目经验、但没做过 FPGA 的开发者。
>
> 核心结论：**嵌入式开发的经验能迁移 70%，但要跨过一道思维坎。**

---

## 零、先建立最重要的那个类比

### 你在手表里是怎么写代码的

```c
while (1) {
    key = scan_key();        // 读按键
    if (key == KEY_UP) {
        menu_move(-1);       // 菜单上移
    }
    update_display();        // 刷屏
    check_battery();         // 查电量
    // ... 一条一条，依次执行
}
```

**关键特征**：CPU 一次只做一件事。`scan_key()` 执行的时候，`update_display()` 在等着。
如果按键处理慢了，屏幕就会卡 —— 于是你学会用**中断**和**状态机**来"假装同时做很多事"。

### 吟游 Loom 里是怎么"写代码"的

```verilog
// 这四块代码，每时每刻都在同时运行
always @(posedge clk) begin
    key_state <= scan_key();      // 读按键
end

always @(posedge clk) begin
    if (key_state == KEY_UP)      // 菜单上移
        menu_pos <= menu_pos - 1;
end

always @(posedge clk) begin
    display_data <= render();     // 渲染
end

always @(posedge clk) begin
    battery <= measure();         // 查电量
end
```

**关键差异**：**这四块是真正的物理并行**，不是"轮流执行"，不是中断模拟。
时钟每跳一次，四块**同时**算完。

> ### 🔑 一句话记住
> **STM32 是"一个厨师做四道菜，轮流炒"；FPGA 是"四个厨师各做一道，同时开工"。**
>
> 而我们的作品要同时发出 4~8 个音 —— **这正是必须要 4~8 个厨师的原因。**
> 也是赛题说的"发挥 FPGA 并行流水线运算优势"。

## 一、逐个阶段对照

### P0 · 开工前置 ⇄ 画板子 / 打样 / 买开发板

| | |
|---|---|
| **手表里是什么** | 画 PCB、打样、采购元器件、装 Keil/CubeMX |
| **这里是什么** | 买 Tang Nano 20K、买 I2S DAC 模块、装 Gowin EDA |
| **你熟悉的** | 一模一样 —— 就是"等快递"和"装环境" |
| **新的东西** | Gowin EDA 取代 Keil/CubeMX |

**类比细节**：

| 手表 | 吟游 Loom |
|---|---|
| Keil / STM32CubeIDE | **Gowin EDA（云源软件）** |
| ST-Link 下载器 | **板载 BL616**（既是下载器又是串口） |
| CubeMX 配时钟树 | **PLL 配置**（27 MHz → 72 MHz，再接分数分频） |
| CubeMX 配引脚复用 | **`.cst` 引脚约束文件** |
| 看门狗、复位电路 | **复位同步模块** |

**这一阶段的感觉**：和手表开机第一步（点亮 LED）完全一样。

### P1 · 仿真基础设施 ⇄ 示波器 + 逻辑分析仪 + 串口打印

| | |
|---|---|
| **手表里是什么** | 写串口打印、接逻辑分析仪抓波形、搭个测试固件 |
| **这里是什么** | 用 iverilog 搭仿真环境、写音频分析工具 |
| **你熟悉的** | 调试前先搭好观测手段 —— 这个意识完全一样 |
| **新的东西** | **仿真取代了"烧进去看看"** |

**为什么这一阶段的地位完全不同？**

| 手表 | 吟游 Loom |
|---|---|
| 改一行代码 → 编译 10 秒 → 烧录 5 秒 → 看现象 | 改一行代码 → 综合布线 **3~10 分钟** → 烧录 → 听声音 |
| 一天能迭代几百次 | 一天只能迭代十几次 |

> ### 🔑 关键认知
> **在 FPGA 里，"烧进去看看"是奢侈品。**
> 所以你必须先在仿真里把逻辑跑对，再上板。
> **这一阶段不是"准备工作"，而是主力工作方式。**

**你在这里会遇到的第一件事**：把仿真输出的数字（PCM 样本）转成 `.wav` 文件，**用播放器听**。
这相当于手表里"用串口打印出传感器读数"，是你在 FPGA 世界里唯一的"printf"。

### P2 · 单声部音频引擎 ⇄ 核心算法模块

| | |
|---|---|
| **手表里是什么** | 写心率算法、写计步算法、写屏幕驱动 |
| **这里是什么** | **相位累加器 + 波表查表 + ADSR 包络** |
| **你熟悉的** | "把核心逻辑写对并验证" 这件事本身 |
| **新的东西** | **用硬件描述语言写数学运算** |

**手表里的心率算法**大概长这样：

```c
uint16_t calc_heart_rate(uint16_t *samples, uint16_t n) {
    uint16_t peak_count = 0;
    for (int i = 1; i < n; i++) {
        if (samples[i] > threshold && samples[i-1] <= threshold)
            peak_count++;
    }
    return peak_count * 60 / (n * SAMPLE_PERIOD_MS);
}
```

**吟游 Loom 里的振荡器**是这样的思路：

```verilog
// 相位累加器：每个采样周期加一次频率控制字
always @(posedge clk) begin
    if (sample_en)
        phase <= phase + inc;          // inc 决定音高
end

// 波表查表：用相位的高位作为地址
always @(posedge clk) begin
    sample <= wavetable[phase[31:20]]; // 输出波形样本
end
```

**思维差异对照**：

| 概念 | C（手表） | Verilog（这里） |
|---|---|---|
| 变量 | `int x;` 存在 RAM | `reg [15:0] x;` 是**一组触发器**，每个时钟都更新 |
| 赋值 | `x = 5;` 立即生效 | `x <= 5;` **下一个时钟才生效** |
| 循环 | `for(i=0;i<8;i++)` 依次跑 8 次 | 写成 8 份电路，**同时**跑 |
| 函数 | 调用时才执行 | 模块一直**挂在**那里运行 |
| 条件 | `if` 就是判断 | `if` 会**综合出选择器电路**（占资源！） |

> ### ⚠️ 最容易踩的坑
> `a = b; c = a;` 在 C 里 c 拿到的是新值；
> 在 Verilog 里如果用 `=`（阻塞赋值），结果**取决于书写顺序**，而且是初学者 bug 的头号来源。
> **记住：时序逻辑一律用 `<=`（非阻塞赋值）。**

**这一阶段你会经历的事**：
- 第一次仿真跑出波形，用频谱工具一看：**峰值不在 440 Hz**
- 查半天发现是相位累加器位宽算错了
- 修正后再看：**峰值正确了** —— 那一刻的成就感，和手表第一次正确读出心率是一样的

### P3 · I2S 输出与上板出声 ⇄ 外设驱动开发

| | |
|---|---|
| **手表里是什么** | 写 SPI 驱动点亮 TFT 屏、写 I2C 驱动读传感器 |
| **这里是什么** | **写 I2S 驱动，输出到 DAC 解码出声** |
| **你熟悉的** | ⭐ **外设驱动是你的强项** —— 这一阶段你会最舒服 |
| **新的东西** | 从"调库"变成"自己用硬件描述时序" |

**为什么说你最舒服**：

I2S 本质是**串行同步协议**，和 SPI 是亲戚：

| 协议 | 时钟线 | 数据线 | 帧同步线 |
|---|---|---|---|
| SPI | SCK | MOSI | SS（片选） |
| **I2S** | **BCLK** | **SDATA** | **LRCLK（左右声道选择）** |

你在手表里配 SPI 的经验，**90% 能直接迁移**：
- 知道要有时钟极性和相位
- 知道数据要在时钟沿稳定
- 知道帧同步信号的作用

**差异**：在 STM32 里你是 `HAL_SPI_Transmit()`，底层寄存器是硬件帮你管的；
在 FPGA 里你要**自己数时钟、自己移位**：

```verilog
// I2S 发送器的核心：移位 + 按位输出
always @(posedge clk) begin
    if (bit_clk_edge) begin
        sdata <= shift_reg[15];
        shift_reg <= {shift_reg[14:0], 1'b0};
    end
end
```

**这一阶段的里程碑**：**喇叭里第一次响出 440 Hz 正弦**。

> 这个时刻相当于手表第一次点亮屏幕 —— **项目从"能不能做"变成"做多少"。**

### P4 · 多声部合成 ⇄ 多任务 / 多线程

| | |
|---|---|
| **手表里是什么** | 用 RTOS 或多个状态机同时跑 UI、传感器、蓝牙 |
| **这里是什么** | **4~8 个声部并行发声** |
| **你熟悉的** | "同时处理多个任务"的架构思维 |
| **新的东西** | ⭐ **这是思维方式转变最大的一步** |

**在 STM32 上实现 4 复音，你会怎么写？**

```c
// 串行处理：一个 CPU 轮流算 4 个声部
for (int v = 0; v < 4; v++) {
    phase[v] += inc[v];              // 依次算
    env[v]   = adsr_step(v);
    mix     += wavetable[phase[v]] * env[v];
}
// 一个采样周期内，4 个声部依次跑完
```

**问题在哪**：
- 采样率 48 kHz → 每 20.8 µs 要算完一轮
- 4 个声部串行没问题
- **32 个声部呢？** 时间不够，声音就会断续
- 这就是赛题说的「**杜绝软件串行运算滞后**」

**在 FPGA 上怎么实现？**

```verilog
// 并行例化：4 份电路同时开工
genvar i;
generate
    for (i = 0; i < 4; i = i + 1) begin : VOICE
        voice u_voice (
            .clk(clk), .inc(inc[i]),
            .gate(gate[i]), .sample(voice_out[i])
        );
    end
endgenerate

// 4 个样本同时到达，一个加法树求和
assign mix = voice_out[0] + voice_out[1] + voice_out[2] + voice_out[3];
```

> ### 🔑 这一阶段你要跨过的坎
> **在 C 里，"同时"是你的想象；在 Verilog 里，"同时"是物理事实。**
>
> 你在手表里用 RTOS 模拟多任务，本质是**快速切换**；
> 这里你**真的复制了 4 份电路**，它们物理上在同一时刻各自运算。

**还有一个新的概念**：**资源占用**。

| 手表 | 吟游 Loom |
|---|---|
| RAM 不够 → 换更大 Flash 的型号 | LUT 不够 → **换更大的 FPGA** |
| 堆栈溢出 → 调大 | 声部太多 → **加法树超时序** |
| 编译报错：内存不足 | 综合报错：**资源超限 / 时序违例** |

**你会第一次体会到**："多一个声部"不是改个数字，而是**真的多占一份硬件资源**。

### P5 · 交互层 ⇄ 传感器采集

| | |
|---|---|
| **手表里是什么** | 读加速度计、读心率传感器、读触摸屏 |
| **这里是什么** | 自研电容触摸 + 超声波测距 + 板载按键 |
| **你熟悉的** | 传感器数据处理、滤波、消抖 |
| **新的东西** | ⚠️ **FPGA 没有 ADC，这是最大的不适** |

**为什么这是最大的不适**：

在 STM32 上读模拟量，你只要：

```c
HAL_ADC_Start(&hadc1);
HAL_ADC_PollForConversion(&hadc1, 10);
uint16_t value = HAL_ADC_GetValue(&hadc1);   // 完事
```

**在 Tang Nano 20K 上**：

| 问题 | 现实 |
|---|---|
| 有 ADC 吗？ | ❌ 板载**没有** ADC |
| 有模拟引脚吗？ | 只有 1 个（接在 BL616 上） |
| 怎么读模拟量？ | **必须用数字方法绕过** |

**这就是我们自研触摸电路的技术根源**：

```
传统做法（STM32）：铜箔 → ADC 读电压 → 判断触摸
我们的做法（FPGA）：铜箔 → RC 充放电 → 测量放电时间 → 判断触摸

把"测电压"转换成"测时间" —— 因为 FPGA 最擅长数时间！
```

> ### 🔑 思维转换
> **在 MCU 世界里，模拟量靠 ADC；在 FPGA 世界里，模拟量靠"转换成时间或频率"。**
>
> 这不是退而求其次，恰恰是**发挥 FPGA 的长处**：
> 72 MHz 的时钟意味着你能分辨约 **13.9 纳秒**的时间差。

**另一个熟悉的东西**：按键消抖。

```c
// 手表里的消抖
if (HAL_GPIO_ReadPin(...) == 0) {
    HAL_Delay(20);
    if (HAL_GPIO_ReadPin(...) == 0) return PRESSED;
}
```

```verilog
// 这里的消抖：计数器数够 20ms 才认可
always @(posedge clk) begin
    if (key_sync != key_stable)
        cnt <= cnt + 1;
    else
        cnt <= 0;
    if (cnt == 20ms_ticks)
        key_stable <= key_sync;
end
```

**注意差异**：C 里的 `HAL_Delay(20)` 是**阻塞**的，这 20ms 什么都干不了；
Verilog 里计数器**在后台跑**，其它逻辑照常运行。

### P6 · 测试模式与验证 ⇄ 出厂的测试模式

| | |
|---|---|
| **手表里是什么** | 出厂测试固件、烧机测试、老化测试 |
| **这里是什么** | **测试模式 + 频谱验证 + 延迟实测** |
| **你熟悉的** | "做个模式专门验证指标"的思路 |
| **新的东西** | 面向评委的自证设计 |

**为什么这个阶段对我们特别重要**：

赛题原文（评分规则第 3 条）：

> 「支持**测试模式**下输出多路不同频率音频，频谱可观测对应数量**独立谱峰**，
> 同时可通过 **RTL 代码**佐证纯硬件实时合成通路，验证**无预录音频播放**行为。」

**翻译成人话**：评委要"数"你有多少个振荡器在响。
所以我们要做一个模式：**一键让 N 个振荡器同时响不同频率**，
评委对着频谱仪一看 —— **有几个峰就是几个振荡器**。

**类比手表**：这就像手表的"工厂测试模式"，按特定组合键进 入，
屏幕显示所有传感器读数、电池电压、屏幕坏点检测。

**还有一件事你会很熟悉** —— **延迟测量**：

| 手表 | 吟游 Loom |
|---|---|
| 测触摸响应延迟：示波器双通道，一路接触摸中断，一路接屏幕刷新信号 | 测音频延迟：示波器双通道，一路接触发信号，一路接音频输出 |
| 目标：<100ms 感觉不到 | 目标：**≤10ms**（赛题硬指标） |

### P7 · 文档与交付 ⇄ 项目报告与答辩

| | |
|---|---|
| **手表里是什么** | 写项目报告、录演示视频、准备答辩 |
| **这里是什么** | 完全一样 |
| **你熟悉的** | ⭐ 全流程你走过一遍 |
| **新的东西** | 交付物里多了一样：**可被审查的 RTL 源码** |

**为什么要特别强调 RTL 就是"无预录"的证据**：

评委看到一段录音触发，会怀疑你是不是在放 MP3。
这时候你**翻开 RTL 代码**，指着 `voice_osc.v` 说：

> "你看，这里是相位累加器，每个采样周期加一次；
> 这里查波表，输出样本。**声音是这么算出来的，仓库里没有任何音频文件。**"

代码是**不会撒谎的一手证据**，说明文档是二手材料。

## 三、你要跨过的三道坎（按难度排序）

### 🥇 第一道坎：串行思维 → 并行思维

| | 手表 | 吟游 Loom |
|---|---|---|
| 执行模型 | 一条指令一条指令 | 所有 `always` 块每个时钟同时跑 |
| "同时" | 靠 RTOS 快速切换**假装** | **物理上真的同时** |
| 循环 | `for` 依次执行 | 复制成多份电路 |

**怎么练**：先用状态机写简单的东西（比如一个呼吸灯），
然后强迫自己画出"这个时刻，哪些寄存器在更新"的时序图。

### 🥈 第二道坎：调试手段从 printf 变成仿真波形

| | 手表 | 吟游 Loom |
|---|---|---|
| 看变量 | `printf("%d", x)` | 波形窗口里看信号 |
| 断点 | 有 | 没有（硬件没有"暂停"的概念） |
| 单步 | 有 | 没有（时钟一直在跑） |
| 迭代速度 | 秒级 | 分钟级（综合布线慢） |

**怎么练**：先学会写 testbench，把"我想看什么"变成"仿真时打印/存盘什么"。

**你唯一的 printf**：把 PCM 样本导出成 wav 文件，**用耳朵听**。

### 🥉 第三道坎：资源管理重新成为核心问题

你在手表里已经很久不用操心内存了（STM32F4 有 192KB RAM，够用）。
在 FPGA 里你要重新开始数：

| 资源 | 20K 有多少 | 类比 |
|---|---|---|
| LUT4 | 20736 | 逻辑门 |
| FF | 15552 | 触发器（存 1 bit 的格子） |
| BSRAM | 容量待核实（官方选题指南未给出） | RAM |
| DSP | 多个 18×18 乘法器（官方未给数量） | 硬件乘法单元 |

**每加一个声部，这些都真的在减少。** 综合报告会精确告诉你用掉了多少。

## 四、你已有的优势（不要浪费）

| 手表里练出来的能力 | 在吟游 Loom 用在哪 |
|---|---|
| ⭐ **外设驱动开发** | P3 的 I2S 发送器（和 SPI 同源） |
| ⭐ **时序概念** | 建立/保持、时钟同步、跨时钟域 |
| ⭐ **中断与实时性直觉** | 理解"为什么延迟必须确定" |
| ⭐ **传感器数据处理** | 消抖、滤波、阈值判断 |
| ⭐ **低功耗/资源意识** | 资源占用与优化 |
| ⭐ **系统集成能力** | 多模块协同、顶层设计 |
| ⭐ **完整项目经验** | 从需求到交付的全流程 |

**最值钱的一条**：你**做过完整项目**。
很多人的问题不是不会写 Verilog，而是不知道怎么把一个东西**从零做到能交付**。
这个你已经在手表项目里学会了。

---

## 五、一个必须提醒的约束

赛题（选题二）原文：

> 「以 FPGA 为核心**并行计算平台**，在**硬件逻辑层**搭建专属实时音频合成引擎」

开放型题目那一条更明确：

> 「体现 FPGA 的性能和非替代性（**不使用 MCU**）」

**这意味着**：

| 手表里的东西 | 能不能用 |
|---|---|
| 用 STM32 跑 FreeRTOS 做任务调度 | ❌ |
| 用软件 DSP 库算音频 | ❌ |
| 用 MCU 合成声音 | ❌ |
| 用 MCU 读传感器、传给 FPGA | ⚠️ 边界模糊，**建议避免** |
| FPGA 纯硬件逻辑做全部音频 | ✅ **唯一正确路线** |

**注意最后那条的陷阱**：Tang Nano 20K 板载有一颗 **BL616 芯片**（负责 JTAG 下载和串口）。
它是板子自带的调试通路，**不是我们用来做功能的**。
为了避免争议，**传感器采集我们也全部用 FPGA 做**（这也是为什么 P5 要自研电容触摸）。

## 六、整体的感觉变化

| 维度 | 手表项目 | 吟游 Loom |
|---|---|---|
| 你的角色 | 软件工程师 + 少量硬件 | **数字电路设计者 + 少量软件（Python 工具）** |
| 主要工作 | 写 C 代码 | 写 Verilog + 画时序 |
| 调试方式 | 在线调试（打断点） | **离线仿真 + 波形分析** |
| 迭代周期 | 秒级 | 分钟级 |
| 最大成就感时刻 | 第一次点亮屏幕 | **第一次听到声音** |
| 最大挫败感时刻 | 屏幕不亮 | **仿真没有输出 / 上板没声音** |

## 七、最后的建议

**不要把这次当成"学一门新语言"，要当成"换一种表达方式"**：

| 你已经在表达的 | 换成的表达方式 |
|---|---|
| `for` 循环 | 生成多份电路（`generate`） |
| `if / else` | 多路选择器 |
| 变量 | 触发器 / 寄存器 |
| 函数调用 | 模块例化 |
| RTOS 任务 | 并行电路 |
| `while(1)` 主循环 | **时钟本身** |

> ### 最重要的一句话
> **在 STM32 里，你写的是"按什么顺序做"；**
> **在 FPGA 里，你写的是"电路长什么样"。**

想通这一点，你已经过半了。
